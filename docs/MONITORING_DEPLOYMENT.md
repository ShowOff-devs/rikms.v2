# Monitoring and alert delivery

RIKMS exposes health signals but monitoring must run independently of the web process, Laravel scheduler, and application queue. The pilot design uses an on-host systemd timer for component checks, an off-host log destination for investigation, and synchronous email and/or webhook delivery for alerts.

For externally operated production dependencies, also run `php artisan rikms:infrastructure-check --write --json` as a deployment gate. Runtime monitoring does not replace provider alerts for database replication, Redis memory, object-storage policy drift, or backup freshness.

## Application configuration

Configure at least one monitored destination before enabling alerts:

```dotenv
MONITORING_ALERTS_ENABLED=true
MONITORING_ALERT_EMAILS=operations@example.gov.ph,security@example.gov.ph
MONITORING_ALERT_WEBHOOK_URL=
MONITORING_ALERT_TIMEOUT_SECONDS=5
MONITORING_ALERT_COOLDOWN_MINUTES=30
MONITORING_SEND_RECOVERY_ALERTS=true
MONITORING_REQUIRE_BACKUP_READY=false
```

`MONITORING_ALERT_WEBHOOK_URL` is a secret when it contains an embedded token. Store it only in the deployment environment or secret manager. Deployed environments reject enabled alerting unless a valid email address or HTTPS webhook exists.

Run a read-only check manually:

```bash
php artisan rikms:monitor-check
php artisan rikms:monitor-check --json
```

Use `--alert` only after recipients are configured. Alerts are delivered synchronously, not through the monitored queue. Repeated identical incidents are suppressed for the configured cooldown; a changed incident bypasses the cooldown, and recovery generates a separate notification.

## Independent timer

After reviewing the service account and deployment path:

```bash
sudo cp deploy/systemd/rikms-monitor.service /etc/systemd/system/
sudo cp deploy/systemd/rikms-monitor.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now rikms-monitor.timer
sudo systemctl list-timers rikms-monitor.timer
sudo journalctl -u rikms-monitor.service --since today
```

The timer runs every five minutes even if Laravel's scheduler or queue worker has stopped. It cannot detect total host or network failure, so an external HTTPS monitor must probe `/up` after the pilot hostname exists.

## Free central logging with Grafana Cloud

Grafana Cloud Free is the recommended pilot destination. Create a separate organization-owned account and stack, then use its **Send Logs / Alloy** connection instructions to create a least-privilege logs-write token. Do not use a personal account or commit the token.

The repository includes `deploy/grafana-alloy/rikms.alloy.example`. Copy and adapt the configuration using the endpoint, username, and token generated by Grafana Cloud. Give Alloy permission to read the journal and restart it:

```bash
sudo usermod -aG adm,systemd-journal alloy
sudo systemctl restart alloy
sudo systemctl status alloy
```

The example keeps only RIKMS, Nginx, PHP-FPM, ClamAV, and MySQL systemd units and uses low-cardinality labels. Verify actual unit names on the Ubuntu host before enabling it. Do not add email addresses, user IDs, IP addresses, request parameters, tokens, or other high-cardinality/private data as Loki labels.

In Grafana Explore, verify entries for `application="rikms"`, then create alerts for error/critical log volume and missing log ingestion. The application monitor remains the primary source for queue, heartbeat, storage, security-event, ClamAV, and backup-readiness alerts.

## Pilot alert drill

In staging, record evidence for each controlled scenario:

1. Stop the queue worker and confirm a critical heartbeat alert.
2. Stop the scheduler timer and confirm a critical heartbeat alert.
3. Create one reviewed failed job and confirm a warning.
4. Make ClamAV unreachable and confirm a critical alert.
5. Temporarily lower a disk threshold and confirm an alert without filling the disk.
6. Restore each component and confirm one recovery notification.
7. Verify the incident and recovery logs in Grafana Cloud.

Record the release SHA, timestamps, recipients, delivery latency, responder, recovery action, and evidence location. Do not inject failures into production.
